# The N150 test box

The performance floor of the port (plan tasks 2, 14, 22) and a second machine for everything a
fast AMD desktop hides: Intel's Mesa drivers, a 4K TV, a small cooler.

| | |
|---|---|
| Name | `steamy`, `steam@192.168.20.239` (SSH key login) |
| CPU | Intel N150: 4 cores / 4 threads, 0.7-3.6 GHz, governor `powersave` |
| GPU | Intel Alder Lake-N integrated (i915), up to 1000 MHz |
| Drivers | Mesa 26.2.5: Vulkan 1.4 (ANV), OpenGL 4.6 / ES 3.2 (iris) |
| RAM | 16 GB, zram swap |
| Storage | 128 GB NVMe |
| Display | 4K TV on HDMI (3840x2160) |
| OS | CachyOS, KDE Plasma (Wayland), Steam installed; no build tools, no root for us |

## Tooling: `scripts/n150.sh`

Builds are made on the main machine and copied; the box only needs the runtime libraries (SDL3,
mpg123, Mesa), which it has. Game runs are headless by default: `scripts/headless.sh` starts a
private, invisible KDE compositor (`kwin_wayland --virtual`, already on the box) for each command,
so the box's screen may be locked, off or in use. The GPU still renders everything; only the
compositor's output goes nowhere. `N150_SCREEN=1` runs on the desktop (the TV) instead, which then
must be unlocked and awake (`n150.sh` checks); TV playtests need that.

| Command | What |
|---|---|
| `deploy` | release builds (GL3 and wgpu), `tests/`, `scripts/` and your game files to `~/revc-bench` |
| `test [--wgpu] [--backend vulkan\|gl] [scenario ...]` | the regression suite on Intel drivers (same references; a second runner beside the local one) |
| `perf [--runs N] [--sizes ...] [--backends ...]` | frame times at the 8 fixed spots, saved under `logs/n150/`, compared with `tests/perf/n150-baseline.txt`: any spot more than 10 % slower fails (`REVC_PERF_TOLERANCE`) |
| `baseline [file]` | accept a perf result as the new baseline (commit it) |
| `soak [--minutes M] [--backend B]` | repeats the spots run for M minutes, logging every run's frame times, failures (game log kept), and every 5 s package temperature, CPU/GPU clocks and the game's memory; reports drift between the first and last quarter (thermal throttling, leaks) and crashes |
| `info` | hardware, driver, temperatures, deployed commit |

Frame times come from `REVC_TEST=spots` (`rust/revc/src/testdrive.rs`): each spot is visited at
the same game time in every run, and the frames of the 3 s before its screenshot are measured
(mean, median, p99, max). `scripts/perf.sh` runs it with VSync and the frame limiter off; it works
on the main machine as well.

## Results

### 2026-11-09: headless baseline (`tests/perf/n150-baseline.txt`)

284b2ab, headless (the default now), 3 runs each, box at 68 C idle at the start. Mean of the 8
spots (the three runs), and the worst p99 of the runs:

| Renderer | 1280x720 | 1920x1080 | worst p99 |
|---|---|---|---|
| GL3 (librw) | 5.59 ms (179 fps) | 5.62 ms (178 fps) | 10.5-12.9 ms |
| wgpu, Vulkan (ANV) | 5.26 ms (190 fps) | 5.36 ms (187 fps) | 8.9-10.7 ms |

Runs agree within 1-4 %. Headless, wgpu on Vulkan is a little faster than GL3, also in its slow
frames. wgpu on GL is not in the baseline (held at 60 fps headless, see Findings).

Full regression suite, headless, GL3 and wgpu Vulkan: all scenarios pass (boot, saveload, formats,
texmods, gamepad, spots) once two problems were fixed: the deploy lacked `assets/` (controller
glyphs: the game fell back to its own button textures), and the gamepad screenshots depended on
timing (below).

### 2026-11-09: first baseline (desktop, superseded)

Release builds of 72b2ef6 plus the VSync fix; spots test settings (noon, sunny, no peds or
traffic), VSync and frame limiter off, windowed on the 4K desktop; one run each. Mean of the 8
spots, and the worst spot's 99th percentile:

| Renderer | 1280x720 | 1920x1080 | worst p99 |
|---|---|---|---|
| GL3 (librw) | 6.00 ms (167 fps) | 6.02 ms (166 fps) | 10.5 ms |
| wgpu, Vulkan (ANV) | 6.25 ms (160 fps) | 6.24 ms (160 fps) | 14.3 ms |
| wgpu, OpenGL (iris) | 9.71 ms (103 fps) | 9.82 ms (102 fps) | 19.2 ms |

- Resolution changes nothing: the N150 is CPU-bound here, at both sizes and on every renderer.
  So 4K output (and supersampling) should be close to free, and the renderer's CPU cost is what
  to optimise.
- wgpu on Vulkan is on par with GL3 on average but its slow frames are slower (p99 14 vs 10 ms);
  wgpu on GL is ~60 % slower: on this machine Vulkan is the backend to default to.
- All comfortably above 60 fps in these (light) scenes; busy streets with traffic are still to
  measure.

### 2026-11-09: 30-minute soak, wgpu on Vulkan, 720p, uncapped

33 spot runs (264 spot measurements), **no failures**, game memory flat at ~197 MB (no leak).
Frame time drifted from 5.25 ms (first quarter) to 5.76 ms (last quarter), +10 %:

| Minutes | Package temp | CPU clock (avg) | GPU clock |
|---|---|---|---|
| 0-3 | 86 C | 2742 MHz | 971 MHz |
| 9-12 | 94 C | 2633 MHz | 978 MHz |
| 27-33 | 95 C (max 97) | 2457-2513 MHz | 964 MHz |

The CPU sits at its thermal limit after ~6 minutes and its clock sinks ~10 %: the frame-time drift
is that throttling (the box is CPU-bound, see above). Uncapped rendering at ~190 fps is the worst
case; capped at 60 fps (the frame limiter, or VSync on the TV) the load and the heat are far lower.
For the N150 quality tier and the AppImage defaults: keep the frame cap on. Also: single runs vary
(this soak's first runs, 5.2 ms, beat the baseline's 6.25 ms taken minutes earlier at a lower
temperature), so baselines should use `--runs 3` on a box that has cooled down.

### Findings on the way

- The wgpu build ignored the game's VSync setting (always waited for vertical blank). Fixed: the
  presenter follows it like GL3's swap interval.
- With the box's screen locked or its display off, the compositor sends no frame callbacks:
  wgpu on Vulkan was throttled to 20 fps, wgpu on GL waited forever (main thread in Wayland
  dispatch), and the test watchdog's `exit()` then hung in the driver's teardown. Now the
  watchdog uses `_exit`, `perf.sh` kills a run after 5 minutes, and runs are headless (see
  Tooling), which needs no screen at all.
- Headless versus desktop, 720p: GL3 5.45 ms, wgpu Vulkan 5.17 ms, close to the desktop numbers.
  wgpu on GL is held at 60 fps by the virtual output (its swap waits for the compositor whatever
  the present mode), so its headless frame times are not comparable: measure wgpu GL with
  `N150_SCREEN=1`.
- The gamepad scenario's screenshots depended on timing, which the N150 exposed: the save pickup
  spins with the absolute game time (the captures were timed from the scenario's start), and after
  30 s without input the player plays a random idle animation. Now the capture times count from a
  multiple of the longest spin period (4096 ms) and the test counts as input every frame
  (`revc_test_touch_input`). Between machines the scene still differs (a pickup bobs by its
  memory address, the clock's minute), so only the help box with the glyphs is compared now
  (`GLYPH_BOX`, top left), and real controllers plugged in are ignored during the scenario (they
  took player 1 from the virtual pads). Main machine and N150 match to 0.002 %.
- With VSync off, on the main machine (RX 9070 XT) wgpu is ~3x slower than GL3 at 720p
  (0.93 vs 0.30 ms a frame): CPU overhead in the renderer (per-frame bind groups and uploads),
  which the N150's slower CPU turns into the p99 gap above. An optimisation pass is due before
  wgpu becomes the default.
